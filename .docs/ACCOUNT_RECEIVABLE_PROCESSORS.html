1. Overview

The Account Receivable Processors are responsible for transforming raw Excel/file data into structured D365 Finance & Operations (D365FO) customer invoice entries. These processors handle the complete lifecycle of data processing including:

  • Data mapping and enrichment
  • Financial dimension parsing and validation
  • Billing code assignment
  • Customer account mapping
  • Invoice creation in D365FO
Key Concept Each processor is specialized for a specific service type (Trucking or Freight) and document type (Invoice or Credit Note), ensuring accurate processing based on business requirements.

6. Validation Rules

Each line is validated against D365FO master data. Validation errors are collected and attached to each line for reporting.

Dimension Validations

All required dimensions are validated to ensure they exist in the D365FO system:

MainAccount

Required - Must exist in Chart of Accounts. Cannot be empty or "000".

Activity

Required - Must exist in Activity dimension. Cannot be "000".

CostCenters

Required - Must exist in Cost Center dimension. Cannot be "000".

BusinessUnit

Required - Must exist in Business Unit dimension. Cannot be "000".

Location

Required - Must exist in Location dimension. Cannot be "000".

Customer

Required - Must exist in Customer dimension. Cannot be "000".

SubCustomer

Required - Must exist in SubCustomer dimension. Cannot be "000".

ChargeType

Required - Must match a billing code in the billing classification.

SalesMan

Required - Must exist in SalesMan dimension. Cannot be "000".

CoordinatorMan

Required - Must exist in CoordinatorMan dimension.

FreightType

Required - Must exist in FreightType dimension.

Direction

Required - Must exist in Direction dimension.

Additional Validations for Trucking

TruckerType

Required - Must exist in TruckerType dimension.

TruckNumber

Required - Must exist in TruckNumber dimension.

Billing Code Validation

The ChargeType dimension is matched against billing codes from the billing classification. If no matching billing code is found, an error is added:

"Could not found a billing code related to this charge type [ChargeType]"
Validation Error Format Errors are stored with a key (dimension name) and message. Example:
Key: MainAccount
Message: "The main account 999999 does not exist in the system."

7. Processing Flow

The processing follows a three-stage pipeline:

1. Format & Enrich
→
2. Validate
→
3. Insert to D365

Stage 1: Format and Enrich (formatAndEnrichAsync)

  1. Load customer-account mappings for the service type (Trucking/Freight)
  2. Convert raw Excel rows to typed AccountReceivableFileModel objects
  3. Group lines by VOUCHER + INVOICE combination
  4. Fetch billing codes for the company
  5. For each group:
    • Sort lines by line number
    • Identify Customer (CUST) and Ledger lines
    • Parse dimension string from ACCOUNTDISPLAYVALUE
    • Apply SubCustomer mapping (lookup invoice account)
    • Match billing code from charge type
    • Create DynAccountReceivableLineDto for each ledger line

Stage 2: Validate (validateAsync)

  1. Load all main accounts from D365FO
  2. Load financial dimension values for each required dimension
  3. Collect charge type dimensions from billing codes
  4. For each AR line, validate all required dimensions
  5. Attach validation errors to each line

Stage 3: Insert to Dynamics (insertIntoDynamicsAsync)

  1. Group validated lines by invoice number
  2. For each invoice group:
    • Create invoice header using the first line
    • Create invoice lines for each detail line
Credit Note Exception Credit Note processors throw an error at the Insert stage. They are designed for validation and data preparation only.

8. Billing Classifications

Billing classifications determine which billing codes are available for charge type matching.

Trucking Classifications

Classification Code Description Credit Note Prefix
INV-TR Trucking Invoice CN (Credit Note)
OR-TR Trucking Order Receipt CR (Credit Receipt)

Freight Classifications

Classification Code Description Credit Note Prefix
INV-FW Freight Invoice CN (Credit Note)
OR-FW Freight Order Receipt CR (Credit Receipt)
OF-FW Freight Ocean Freight CN (Credit Note)

Classification Detection (Credit Notes)

For credit notes, the billing classification is automatically determined from the JOURNALNAME or INVOICE fields:

// Trucking Credit Note Detection Logic: if (journalName.includes('or-tr') || invoice.includes('or')) return 'OR-TR'; if (journalName.includes('inv-tr') || invoice.includes('inv')) return 'INV-TR'; // Default: INV-TR // Freight Credit Note Detection Logic: if (journalName.includes('or-fw') || invoice.includes('or')) return 'OR-FW'; if (journalName.includes('of-fw') || invoice.includes('of')) return 'OF-FW'; if (journalName.includes('inv-fw') || invoice.includes('inv')) return 'INV-FW'; // Default: INV-FW

// Trucking Credit Notes: 'INV-TR' → Prefix: 'CN' (e.g., CN-00001) 'OR-TR' → Prefix: 'CR' (e.g., CR-00001) // Freight Credit Notes: 'OR-FW' → Prefix: 'CR' (e.g., CR-00001) Other → Prefix: 'CN' (e.g., CN-00001)

The DOCUMENT field is formatted to 8 digits for the CreditNoteInvoiceRef:

// Input: "123/2024" → Output: "00000123" // Input: "45" → Output: "00000045" // Input: "" → Output: "00000000"

10. Special Behaviors

Tax Group Derivation

The SalesTaxGroup and SalesTaxItemGroup are derived with special rules:

// SalesTaxGroup Logic: if (!SALESTAXGROUP || !ITEMSALESTAXGROUP) return 'Non-Taxabl'; if (ITEMSALESTAXGROUP.includes('VAT-0%')) return 'Non-Taxabl'; return SALESTAXGROUP; // SalesTaxItemGroup Logic: if (!ITEMSALESTAXGROUP) return ''; if (ITEMSALESTAXGROUP.includes('14%SUPPLIE') || ITEMSALESTAXGROUP.includes('14')) return 'VAT-14%'; if (ITEMSALESTAXGROUP.includes('VAT-0%')) return ''; return ITEMSALESTAXGROUP;

SubCustomer Mapping

When processing, the SubCustomer dimension value is mapped to the corresponding invoiceAccount from the customer-account mapping master data:

  1. Check if the Customer dimension exists in the account mappings
  2. If found, look up the SubCustomer in the same mappings
  3. If a match is found, replace SubCustomer with the invoiceAccount value

Location Normalization

Location values are normalized during processing:

  • CAI (case-insensitive) is converted to 002
  • When converting back to string, 002 is converted to cai

Date Coercion

The processors handle multiple date formats:

  • Date object: Used as-is
  • String: Parsed using JavaScript Date constructor
  • Number (Excel serial): Converted using formula: (value - 25569) * 86400 * 1000 milliseconds

Terms of Payment Calculation

For invoices, payment terms are calculated as the number of days between TRANSDATE and DUEDATE:

// Result format: "X Days" termsOfPaymentDays = Math.ceil((DUEDATE - TRANSDATE) / (1000 * 60 * 60 * 24)); TermsOfPayment = `${termsOfPaymentDays} Days`;

11. Error Handling

Errors are handled at multiple levels and collected for reporting:

Validation Errors

Each DynAccountReceivableLineDto can accumulate validation errors via the AddError(key, message) method. These errors do not stop processing but are attached to the line for reporting.

Common Validation Error Messages

Error Key Message Pattern Cause
MainAccount "Main Account is required" Missing or empty value
MainAccount "The main account {value} does not exist in the system." Value not in Chart of Accounts
CustomerDimensions "Customer is required" Missing, empty, or "000"
CustomerDimensions "The dimension {value} does not exist in the system." Value not in Customer dimension
BillingCode "Could not found a billing code related to this charge type {chargeType}" No matching billing code for ChargeType

Processing Errors

Credit Note Insert Attempt Calling insertIntoDynamicsAsync on a credit note processor throws:
"InsertIntoDynamicsAsync is not implemented for credit notes"
