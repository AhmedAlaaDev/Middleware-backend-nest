1   What the Cash Module Does

The Cash Module is part of the Data Migration Middleware system. Its purpose is to receive cash transaction data exported from the ICT source system in Excel format, validate and clean it, convert it into the format required by Microsoft Dynamics 365 Finance & Operations (D365FO), and store the results in the system for review and download.

The module handles four distinct transaction types, each uploaded through a dedicated endpoint:

Transaction Type Direction Business Line D365FO Journal Name
Cash-In Freight Inbound Freight / Forwarding Cust-Pay
Cash-In Trucking Inbound Fleet / Trucking Cust-Fleet
Cash-Out Freight Outbound Freight / Forwarding CashOut
Cash-Out Trucking Outbound Fleet / Trucking CashOut-Fleet
Cash-In vs Cash-Out: Cash-In transactions represent money received from customers (customer collections, down-payments, etc.). Cash-Out transactions represent payments made by the company (custody settlements, vendor payments, direct disbursements, etc.).

2   Excel Input Data

Each upload consists of a single Excel file (.xlsx or .xls) and an optional Company ID. The Excel file must contain one row per journal line as exported from the ICT source system.

Important: Each of the four transaction types must be uploaded separately through its own dedicated upload form. A single file cannot mix Freight and Trucking, or Cash-In and Cash-Out transactions.

3   Validations & Business Checks

Before any data is saved, the system runs a series of checks. Rows that fail validation are flagged with an error message. The batch is still saved so you can review and correct the issues before re-uploading.

File-Level Checks

  • The uploaded file must be in Excel format (.xlsx or .xls). Other file types are rejected immediately.
  • An empty file with no data rows is rejected with an error.
  • Each batch is limited to a maximum of 1,000 lines. Larger files must be split before upload.

Invoice Balance Check

  • For each unique invoice, the total debit amounts must equal the total credit amounts. Exchange rates are taken into account during this check. An unbalanced invoice is flagged as an error on all its related lines.

Dimension Validation

  • Each line's financial dimensions are checked against the dimension master data.
  • For Trucking transactions: any line with Account Type = Ledger must have a value for the TruckerType dimension.
  • For Freight transactions: FreightType and Direction dimensions must be present.

Cash-In Invoice Checks (against D365FO)

Cash-In transactions are matched against existing invoices in D365FO. The following checks apply:
  • Invoice must exist: the invoice reference in the Excel file must correspond to an existing free-text invoice in D365FO. If not found, the line is flagged.
  • Invoice must be posted: only invoices that have already been posted (confirmed) in D365FO can be settled. Unposted invoices are flagged.
  • No duplicate settlement: if the same invoice number appears more than once in D365FO, the line is flagged and the duplicates must be resolved in D365FO first.

Special Handling on Cash-Out

  • Lines with SafeType = "Custody Settlement" or "Vendor Payment" are automatically separated from the main cash journal and routed to their own dedicated processing flows. They do not appear in the main cash output.
Validation Errors: Lines with errors are included in the saved batch but are clearly marked. You should download the mapped data file to review all flagged rows before proceeding further.

5   Data Transformation & Mapping

Once validation is complete, the system transforms the source data into the structure required by D365FO’s Customer Payment Journal. The key transformations are described below.

How Source Rows Are Converted to Journal Lines

The ICT source system exports one row per accounting entry side. This means a single payment transaction typically appears as at least two rows in the Excel file — one row for the customer (who paid) and one row for the ledger account (where the money was recorded).

The system analyses these rows and pairs the two sides together to form a single destination journal line. Each destination line carries both sides of the transaction:

  • Account side: the customer who made or received the payment.
  • Offset side: the ledger or bank account on the other side of the transaction.

As a result, the number of output lines in the mapped file is typically half the number of source rows — or fewer, when settlement lines are filtered out (see Section 3).

Example — Simple Payment (2 source rows → 1 journal line)
#Account TypeDirectionAmountInvoice
1CustomerCredit (payment received)5,000 EGP12345/OF-FW
2LedgerDebit (recorded to account)5,000 EGP12345/OF-FW
↓
1 destination journal line:  Account = Customer  |  Offset = Ledger Account  |  Amount = 5,000 EGP  |  Invoice = 000012345/OF-FW
The output row count will differ from the input row count. This is expected behaviour. If you upload 100 source rows, you may receive 50 or fewer destination journal lines. The mapped data file shows exactly how source rows were combined.

How Transactions Are Grouped into Batches

After the journal lines are built, the system groups them into separate batches before assigning batch and voucher numbers. A batch is never allowed to mix different payment instrument types. The system uses three groups:

💵 Cash
Transactions paid in physical cash
✅ Cheque
Transactions paid by cheque
★ Other
Visa, Transfer, Deposit,
POS, PrePayment, etc.

All Cash transactions are processed first as a group, then Cheque transactions, then all Other types. Within each group, the standard rules continue to apply: transactions must stay within the same calendar month, and a single batch cannot exceed 1,000 lines.

Why does this matter? Keeping payment instruments in separate batches ensures that D365FO receives clean, consistent journals. Cash payments and cheque payments are never mixed in the same voucher, which simplifies reconciliation and avoids posting errors.

In summary, a new batch is started whenever any of the following occurs:

  • The payment instrument group changes (e.g. moving from Cash lines to Cheque lines).
  • The transaction month changes (e.g. moving from March entries to April entries).
  • The current batch reaches the 1,000-line limit.

Journal Assignment

Each batch is automatically assigned to the correct D365FO journal based on the transaction type (see the table in Section 1). The posting profile is set to Cust-PP for all customer lines.

Payment Reference Generation

  • If the source row contains a valid Payment Reference value, it is used as-is.
  • If the payment reference is blank, zero, or a placeholder value (such as N/A, 0, 000), the system automatically builds a reference from the transaction description combined with the business line label (e.g. "Settlement description – Freight").

Invoice Number Normalisation

  • Invoice numbers are standardised to ensure they match D365FO format.
  • Arabic freight description text is mapped to the standard prefix OF-FW.
  • Import and warehouse invoice references are normalised to the prefix INVOICE.
  • Invoice numbers are padded with leading zeros to a consistent 9-digit length (e.g. 12345 becomes 000012345).

Customer Name Lookup

The system looks up the customer’s full name from the master data using the customer account number and populates the CustomerName field automatically.

Exchange Rate Lookup

Exchange rates are retrieved automatically from the master data based on the currency code and transaction date. The source exchange rate is used if provided; otherwise, the system fetches the applicable rate.

Financial Dimensions

Dimensions are extracted from the offset (ledger) line of each transaction pair and applied to the customer payment line. The dimension string is stored separately for both the account side and the offset side.

6   Expected Output

After a successful upload, the system saves a data batch containing two versions of the data:

  1. Source Data (Raw): An exact copy of what was read from the uploaded Excel file, stored row by row. This serves as a permanent audit trail of what was submitted.
  2. Mapped Data (Enriched): The transformed and consolidated version, ready for D365FO import. This includes all generated fields, lookups, normalised values, and validation results. Lines with errors are clearly marked with an error description.
Output row count is different from input row count. The source file contains one row per accounting entry side (debit or credit). The mapped file contains one row per complete journal line (both sides combined). A file with 200 source rows typically produces around 100 mapped journal lines — or fewer if some lines are filtered out as custody settlement or vendor payment entries. This difference is normal and expected.

Each batch is given a unique Batch ID and a descriptive name that includes the transaction type, business line, date, and an auto-incremented counter (e.g. Cash-In Freight – 2026-04-27 – #001).

Successful batch: When all rows pass validation, the batch status is set to Ready. You can then download the mapped data for review or manual import.
Batch with errors: When one or more rows have validation issues, the batch is still saved. The status indicates the number of error lines. Download the mapped data file to see the exact error message on each affected row.

8   Current Limitations

⚠  Automatic posting to D365FO is not currently available for the Cash Module.
The system can process, validate, and map cash data, but it cannot automatically submit the data to D365FO at this time. The “Post to D365FO” feature is under development and will be made available in a future release.

For the time being, the recommended workflow is:

  1. Upload the Excel file for the relevant cash type.
  2. Review the batch result and check for any validation errors.
  3. Download the Mapped Data Excel file.
  4. Manually import the mapped data into D365FO using the standard D365FO data management tools, if required.

Other Known Limitations

  • Separate uploads per type: Each of the four cash transaction types (Cash-In Freight, Cash-In Trucking, Cash-Out Freight, Cash-Out Trucking) must be uploaded separately. A single file cannot contain mixed types.
  • Maximum 1,000 lines per batch: Files with more than 1,000 journal lines must be split into multiple files before upload.
  • Month isolation: All lines in a single batch must belong to the same calendar month. Cross-month batches are not supported.
  • Payment instrument separation: Cash, Cheque, and Other transactions are placed into separate batches automatically. If your file contains a mix of payment instruments, the system will produce multiple batches within the same upload.
  • Custody Settlement & Vendor Payment (Cash-Out): Lines classified as Custody Settlement or Vendor Payment are automatically removed from the main cash output and routed to separate processing flows. They will not appear in the Cash-Out mapped data file.
  • Cash-In invoice verification: Cash-In processing requires that matching free-text invoices already exist and are posted in D365FO. If D365FO connectivity is unavailable at the time of upload, invoice validation cannot be completed.
  • Output row count differs from input row count: This is by design. See Section 6 for a full explanation.
